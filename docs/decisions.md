# 実装判断の記録（decisions）

企画書に明記が無く、実装で決めた点を残す。**推測で埋めない**（企画書 §12）ため、
「企画書のどこを根拠にどう決めたか」「反転するとしたらどこを直すか」をセットで書く。
異論があればここを起点に差し戻せる。

---

## D-001 空シードのフォルダは 0件（既定フォルダを作らない）

- **根拠**: 企画書 §10-5 は「Folder 0（or 既定フォルダ1のみ）」と両論併記。
  §1-4 が基準状態を「まっさら」、§1-4/§6-4 が最重要状態を **empty（0件）** と定めているため、
  `/folders` が空状態で始まる 0件 を採用した。作成フローも「フォルダ作成」から始まるのが自然。
- **影響**: `/folders` の初期表示が empty 状態。beyondページはフォルダ未所属でも作成できる
  （`folder_id: null` を許容）ので、フォルダを作らなくても作成フローは詰まらない。
- **反転する場合**: `mock-server/store/seed-empty.ts` の `folders: []` に既定フォルダを1件足す。

## D-002 ベンダー側カタログは空シードでも保持する

- **根拠**: 企画書 §10-5 は「Media（媒体）ロスターだけは選択肢として固定保持」と書く。
  Media が固定保持される理由は「作成時に選べるように」＝**アカウントの新旧に依らず存在する選択肢だから**。
  同じ性質のもの（新規アカウントでも画面に出るベンダー側マスタ）を同じ扱いにした。
- **対象**: 媒体ロスター8種 / 初期プラン1 / アドオンカタログ / 権限一覧 / セミナー / 紹介記事 / 審査機関マスタ / ASP名マスタ
- **対象外（0件のまま）**: フォルダ・beyondページ・記事・Version・CV・タスク・広告アカウント・ドメイン・タグ
- **注意**: 企画書の文言は「Media **だけ**」なので、これは**文言の拡大解釈**にあたる。
  厳密に Media のみとしたい場合は `mock-server/store/catalog.ts` を空にすれば反転できる（1ファイル）。
  → **要確認事項**。

## D-003 「作成直後は0値、ダミーの流入が乗ると数値が付く」の実装

- **根拠**: 企画書 §10-9 の当該文。§10-5 の「時系列（チャート/レポートが常に非空）」は
  populated モード側の記述と解釈した（空シードでは AbTest が0件なので、そもそも系列が立たない）。
- **実装**: 日次メトリクスは**シードで作らない**。CV速報（ActionCable モック）が
  **公開中Versionが存在するときだけ** 合成CVを push し、その CV がストアの日次メトリクスに積まれる。
  → 新規アカウント＝全部0 → beyondページ作成・公開 → 数値が付き始める、という見え方になる。
- **決定論との整合**: シードデータは決定論（§10-5）。セッション中に積み上がる分はセッション状態であり、
  reset（§10-9）で消える。両者は別物として扱う。

## D-004 state_id は `<slug>__<state>` に統一

- **根拠**: 企画書 §7-2 の命名規約。§8 のスターター例には `ab_tests-articles-editor__default` という
  別表記もあったが、台帳を機械生成・機械検査する以上、slug から一意に導出できる形が必要。
- **実装**: `tools/traceability/build.ts` が `capture/capture-plan.json` から生成する。

## D-005 pc / sp は「状態」ではなく「ビューポート」

- **根拠**: 企画書 §13-A は 1440×900(PC) と 430×932(SP) の2ビューポートで**各状態を**比較すると書く。
  pc/sp を state として数えると母集合が二重計上され、§8 の台帳がぶれる。
- **実装**: `capture-plan.json` の `viewports` をルート属性として持ち、
  撮影枚数 = states × viewports で数える。

## D-006 一覧系ルートの `default` と `empty` は empty に一本化

- **根拠**: 基準状態が新規アカウント（§1-4）なので、一覧ルートの `default` は定義上 `empty` と同一画面になる。
  2つに分けると同じスクリーンショットを2回撮ることになり、台帳も水増しされる。
- **反転する場合**: populated フェーズで `normal`（priority=3）が有効化されるので、そのとき自然に分岐する。

## D-007 モックサーバーの依存を最小化（faker を使わない）

- **根拠**: 企画書 §10-5 は「faker等を固定seedで」と書くが、要件は**決定論**であって faker ではない。
  §12 の KISS/YAGNI に従い、外部依存のバージョン差で決定論が揺れないよう、
  mulberry32 + FNV-1a を `mock-server/store/rng.ts` に自前実装した（約40行）。
- **反転する場合**: `rng.ts` の差し替えのみ。

## D-008 grepゲートの自己除外は3ファイルのみ

- 検出パターンの定義元だけを除外し、理由を `docs/scrub-policy.md` に明記した。
  **除外を増やすときは必ず理由を書く**（黙って増やすのはゲートの無効化と同じ）。

## D-009 採取は「実データ入りの既存アカウント」のみ（新規アカウント発行不可）

- **確認日**: 2026-08-31（ユーザー回答: 新規アカウントは発行できない）
- **影響**: 企画書 §5-7 の観測フロア問題が全面的に効く。基準状態が「新規アカウント（空）」なのに、
  採取元アカウントには実データがあるため、**アカウント全体の一覧の空状態は原理的に撮れない**。
- **対応（3分割）**: 各状態に `capture_mode` を持たせた。
  - `read-only`(104) … 見るだけ。シェル・CSS・各ルートのガワ・タブ・フォームのバリデーション等
  - `write-production`(165) … **本番に採取用エンティティを作ってから撮る**。
    `:uid` 配下（entity スコープ・24ルート）は**新しく作れば配下が空**なので、既存アカウントでも空状態を観測できる。
    エディタ・レポート・スプリット設定・離脱ポップアップ等、Tier2 の中核はこれで採れる。
  - `hand-built`(33) … アカウント全体の一覧の空状態。実CSS＋データモデルから手構築（§5-7(b)）。
    代替として **filter-empty**（一致しない語で検索した空結果）を撮り、同じ空状態コンポーネントを流用する。
- **重要な緩和策**: hand-built の33ルートの多くは、その機能を使っていなければ**既に空**。
  採取の Step 0 で棚卸しし、空だったものは read-only に格下げする（`docs/capture-manifest.md`）。
- **本番書き込みのリスク**: 実レコードを作るため、採取用の親フォルダ配下に隔離し `【採取用】` 接頭辞を付け、
  **公開(publish)は確認ダイアログまでで止め**、採取後に削除する。詳細は `docs/capture-manifest.md`。

## D-010 再現対象は「旧UI」のみ（新UIは対象外）

- **確認日**: 2026-08-31（実機確認＋ユーザー回答）
- **実測**: サイドバー最下部に `新UI / OFF` のトグルボタンがある（`<button class="e316ctq1 css-7y1g32 ehjzppn1">`）。
  つまり本アプリには**旧UIと新UIの2系統**が存在する。企画書 v2.0 にこの記述は無い（調査時の見落とし）。
- **決定**: **再現するのは旧UI（トグルOFFの状態＝既定で表示されるUI）のみ。** 新UI側の画面は作らない。
- **影響**:
  - 採取は必ず「新UI OFF」の状態で行う。採取中にトグルを押さない（採取ビルドの混在と同じ事故になる）。
  - トグルボタン自体はサイドバーの一部なので**見た目は再現する**が、押しても何も起きない（または無効）扱いにする。
  - 企画書 §16-3 の「`/ab_tests/:uid/articles` と `/folders/:.../edit` の関係」は、
    この2系統UIと関係している可能性がある（旧UI入口 / 新UI入口）。採取時に必ず突合する。
- **反転する場合**: 新UIも対象にするなら、ルート母集合・状態インベントリ・採取計画がもう一段増える（別企画）。
